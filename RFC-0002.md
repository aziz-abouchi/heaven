# RFC-0002 — Bitstrings : patterns binaires en Heaven

Status: Draft
Version: 0.1
Target: Heaven v0.2 (P1-P2) / v0.3 (P3-P4)
Author: Aziz Abouchi
Date: 2026-10-08

# 1. Motivation

Heaven emprunte déjà à Erlang `spawn`/`tell`/`recv`. Il lui manque le
binary pattern matching — la fonctionnalité qui a fait la légende d'Erlang
en télécom (parseurs d'en-têtes en trois lignes, centrales AXD301).

Tout ce qui est planifié en aval a besoin d'une couche codec :

| Consommateur | Besoin |
|---|---|
| DB (Bitcask, Datalog) | encodage des enregistrements, clés/valeurs |
| Frames WebSocket / HTTP-2 | champs bit-à-bit non alignés octet |
| Sessions MPST | format wire des messages |
| ZKP (Fiat-Shamir) | sérialisation des transcripts |

Personne ne peut *prouver* ses codecs. Heaven peut :
`theorem roundtrip : decode (encode v) = v`.

# 2. Objectifs

* Destructuration en position de pattern : `version <<ver:4, _:28>> = ver`
* Construction en position d'expression : `<<4:4, 5:4>>`
* Sucre PUR : abaissé en arithmétique avant évaluation — l'invariant des
  6 primitives tient, `ExtensionNotLowered` ne peut jamais se déclencher
* Provable : idempotence du parseur, roundtrip encode/decode

# 3. Non-objectifs (v0.2)

* PAS de nouveau type dans le noyau — `expr.zig` inchangé. `BitString`
  ne deviendra un type que sur preuve de nécessité.
* PAS de cible de performance sur le non-aligné (Erlang a mis des années ;
  fast path alignée octet en v0.2, slow path en v0.3).
* PAS de compatibilité Erlang au-delà de l'inspiration.

# 4. Syntaxe

EBNF (à synchroniser dans GRAMMAR.md — grammar.js reste la vérité) :

    BinaryPattern ::= "<<" Segment { "," Segment } ">>"
    Segment       ::= Identifier ":" Size [ Spec ] | "_"
    Size          ::= Entier
    Spec          ::= "bits" | "little" | "big" | "signed" | "unsigned"
    BinaryExpr    ::= "<<" SegExpr { "," SegExpr } ">>"
    SegExpr       ::= Expr ":" Size [ Spec ]

Sémantique des segments :

| Segment | Signification | Défaut |
|---|---|---|
| `x:4` | entier sur 4 bits | 8 si omise |
| `x:4/little` | boutisme little | big |
| `x:4/signed` | signé | non signé |
| `rest:bits` | le reste (dernière position uniquement) | — |
| `_` | ignorer | — |

En v0.2, l'opérande est un `Int` (≤ 64 bits). `rest:bits` et les tampons
> 64 bits arrivent en v0.3 (bitreader sur std/array.hvn).

# 5. Exemples de référence

    -- IPv4 : premier mot 32 bits
    version <<ver:4, ihl:4, _tos:8, _len:16>> = ver

    -- varint QUIC : LA démo
    varint <<0:2, v:6>>  = v
    varint <<1:2, v:14>> = v
    varint <<2:2, v:30>> = v
    varint <<3:2, v:62>> = v

    encode_varint 5 = <<0:2, 5:6>>

    theorem varint_roundtrip : decode (encode v) = v
    prove varint_roundtrip by { cases; simplify }

# 6. Abaissement (le cœur du RFC)

Précédent : `ForExpr` est déjà désucré en `map`/`filter` dans
`src/core/parse.zig`. Les bitstrings suivent le même chemin.

Destructuration (alignée octet) :

    version <<ver:4, _:4, _:24>> = ver
            ↓ parse.zig
    version w = let ver = (band (shr w 28) 15) in ver

Construction :

    <<a:4, b:4>>
            ↓
    (bor (shl (band a 15) 4) (band b 15))

Opérateurs requis : `shr`, `shl`, `band`, `bor`.
**À vérifier par lecture** : leur présence dans les magics existantes
(heaven_expr.zig:2006) — GRAMMAR.md liste déjà `>>` en opérateur, la
forme exacte (infixe vs magic) sera fixée par cette lecture. Si absents :
4 magics fines, style D14.
